= Workshop conclusion

Congratulations! You've successfully completed the Introduction to Automation Portal workshop.

== What you accomplished

You practiced Automation Portal as a broader Ansible Automation Platform experience: **discover** content across Hub and Git, **create** assets such as execution environments, and **share** governed capability with domain teams through the catalog. Controller remains where you operate automation at scale; the portal helps more people find, build, and use that automation under AAP identity and RBAC.

**Module 1: Configure Ansible Automation Platform for Automation Portal**

You set up governed access across AAP and the portal:

* Created three teams for cloud, network, and RHEL domains
* Assigned permissions to job templates, inventories, and credentials
* Built portal RBAC policies for catalog and scaffolder access
* Confirmed content synchronization between AAP and the portal

**Module 2: User persona testing**

You validated that sharing capability works for different SMEs:

* Cloud administrator access to AWS, Azure, and GCP automation
* Network administrator access to network job templates
* RHEL administrator access to Linux automation and select cloud templates

**Module 3: Surveys and custom templates**

You improved how shared automation is presented and launched:

* Modified job template surveys in AAP and saw them in the portal
* Imported a custom dynamic template from Git
* Launched automation with richer options than a basic survey

**Module 4: Content discovery**

You used the portal to find automation that was previously scattered:

* Browsed discoverable Git repositories
* Explored collections with filters
* Distinguished Hub-backed content from custom collections such as `parasol.*`

**Module 5: Build and use an execution environment**

You closed the loop from discovery to a runnable Network job:

* Built an EE as the network automation developer using custom and Hub collections
* Published to the lab GitHub repository and followed Actions
* Saw how Hub and registry credentials support the image push
* Had the platform admin attach the EE to a Network job template
* Launched the job from the portal catalog as an end user

== Learning outcomes

By completing this workshop, you should now understand:

* **How Automation Portal fits AAP** for discovery, guided creation (such as EE Builder), and sharing capability with SMEs, while Controller operates automation at scale
* **How RBAC works across AAP and Automation Portal** for users, teams, organizations, and least-privilege access
* **How to configure team-based access** so domain experts see the right templates, inventories, and credentials
* **How portal permission policies** control catalog and scaffolder access
* **How synchronization works** for organizations, users, teams, and job templates (including manual sync)
* **How surveys and custom dynamic templates** improve the launch experience for shared automation
* **What content discovery provides** as a searchable catalog over Hub and Git
* **How EE Builder fits the portal** from visual definition through GitHub build to use on a job template

== Key takeaways

=== Technical skills gained

* **Governed access** across AAP and Automation Portal so users see and run only what they are authorized to use
* **Portal sync** of organizations, users, teams, and job templates from AAP
* **Share-path UX** with surveys and custom dynamic templates
* **Content discovery** for repositories and collections without hunting Hub and Git separately
* **Execution Environment Builder** to generate definitions, land them in GitHub, and wire the image to job templates
* **Team-based permissions** organized by IT domain

=== Business value delivered

Automation Portal helps address adoption and sprawl:

* **Broader adoption** as domain experts can find and use automation without becoming platform engineers
* **Less content hunting** when Hub collections and Git repositories surface in one catalog
* **Faster path to reusable assets** such as EEs created with guided tools and published through Git
* **Governance retained** through AAP identity, teams, and RBAC when capability is shared
* **Less load on the automation team** when SMEs can launch authorized work themselves

== Architecture summary

Your lab environment included:

* **Ansible Automation Platform 2.7** as the control plane for credentials, inventories, projects, job templates, and Hub
* **Automation Portal** for content discovery, EE Builder, and the self-service catalog (synced with AAP)
* **Private Automation Hub** and the lab **GitHub** organization for collections and EE build repositories
* **OpenShift** hosting AAP and the portal

== Next steps

=== Plan what to take back

* Which teams need shared catalog access first, and which templates should they see?
* Which repositories and collections should content discovery make visible?
* Where will EE Builder help standardize images for domain teams?
* What RBAC and review process will you use as the library grows?

=== Identify pilot users

Select a small group of SMEs from different domains (cloud, network, Linux, and others). Include people with different automation experience, and gather feedback on discovery, creation, and shared launch.

=== Grow the library thoughtfully

* Automate common manual tasks and expose them through the catalog with clear surveys
* Keep Hub and Git content discoverable where it helps teams reuse work
* Document use cases and expected outcomes for shared templates and EEs

=== Establish governance

* Who approves new templates, discovered repos, and EE definitions?
* How are permissions reviewed?
* What monitoring and auditing do you need?
