= Build and use an execution environment

== Learning objectives

By the end of this module, you'll be able to:

* Describe why teams need purpose-built **execution environments (EEs)**
* Use Automation Portal’s **Execution Environment Builder** as a **network automation developer** to build and publish a cutsom EE
* Assign the new EE to a job template in AAP and run automation with it

In Module 4 you unlocked content discovery for `portal-users` and explored collections and Git content.
In this module the **network team** needs new automation that depends on collections you can now see in the portal.
A network automation developer has already written the playbook, but they still need a matching EE before operators can run it reliably.

You will:

. Join the lab GitHub org/team as `networkuser1`
. Build the EE in the portal as the network automation developer
. Review the GitHub pull request and Actions build
. Switch to the platform admin to attach the EE to a Network job template in AAP
. Launch the job from the portal catalog so end users can consume the result

NOTE: When switching users, **log out of both Ansible Automation Platform and Automation Portal** before signing in as the next user. Prefer a **new browser tab** for the portal link (especially before GitHub OAuth).

[#ee-scenario]
== Scenario: Network automation needs a new EE

Your **network operations** team wants new device-onboarding automation.
A **network automation developer** built the playbook for **`Network/Onboard Network device`** and needs an EE that includes the collections and packages that automation depends on:

* **`cisco.ios`** and **`ansible.netcommon`** from Private Automation Hub **`rh-certified`** (Red Hat certified)
* **`network.acls`** from Private Automation Hub **`validated`** (Ansible validated content)
* **`community.general`** from Private Automation Hub **`community`**
* **`parasol.network`** from Private Automation Hub **`published`** (Parasol custom collection from Module 4)
* System package **`git`** and Python package **`paramiko`**

With AAP 2.7, Automation Portal provides a **visual Execution Environment Builder** that lets you choose collections and options through a guided point-and-click experience, then generate the definition into Git and kick off the build pipeline.

[#github-build]
== Review the pull request and build from the portal

Stay on the progress page after you submit. When the GitHub steps finish, use the action buttons at the bottom of that page.

=== Pull request and definition files

* Click **GitHub Pull Request**.
* Review the changed files. You should see a directory named after your EE (for example `network-ops-ee/`) that includes:
** `network-ops-ee.yml` (the EE definition; it is named after the EE, not `execution-environment.yml`)
** `catalog-info.yaml` (registers the definition in the portal Catalog)
** updates under `.github/workflows/ee-build.yml`

✅ **Expected result**: The PR shows the EE definition content you configured. The `main` branch still looks nearly empty until you merge.

* **Merge** the pull request into `main` so the EE definition and `catalog-info.yaml` land on the default branch.

=== GitHub Actions build

* Return to the portal progress page and click **Github EE Build Workflow Run**.
* Or open the repository **Actions** tab and select the **Execution Environment Build** run.
* Open the run and watch the job steps as GitHub Actions builds the image, runs its checks, and publishes the EE to Private Automation Hub.

[IMPORTANT]
====
This can take several minutes. Stay on the run page and expand failing steps if anything turns red. Ask your facilitator before inventing new registry passwords.
====

✅ **Success indicator**: The workflow concludes successfully (green).

[#hub-registry]
== How the image reaches Private Automation Hub (brief)

You do not need to configure secrets in this exercise. They were set when the lab was provisioned, but you should understand the pattern:

* The GitHub repo stores **Actions secrets / variables** used by `ee-build.yml`
* **Galaxy / Hub tokens** allow the build to pull collections from Private Automation Hub during the image build
* **Registry username / password** allow the workflow to **push** the finished EE image to the Hub registry
* Organizations can point the same style of workflow at **other registries** (Quay, mirrored registries, etc.) by changing registry URL and credentials. Hub is the default target in this workshop

[NOTE]
====
**Key learning**: EE Builder generates the definition and kicks the build; **GitHub Actions + Hub credentials** perform the actual image build and publish.
The network developer can drive that path from the portal; platform teams still own registry and secret hygiene.
====

Optionally confirm in AAP **Automation Hub** that a new execution environment image or EE entry appeared for your build (name/tag from the template). Refresh if needed. Indexing can lag slightly behind a green Actions run.

[#use-ee-on-jt]
== Platform admin: attach the EE to a job template in AAP

Log out of Automation Portal if you are still signed in as `networkuser1`.
Log in to the link:{aap_controller_url}[Ansible Automation Platform^] as `{aap_admin_username}` with password `{aap_admin_password}`.

=== Add the Hub EE to Controller

* Go to **Automation Content → Execution Environments**.
* Find **`network-ops-ee`**.
* Open the kebab menu and select **Use in Controller**.

image::m05-ee-use-in-controller.png[AAP Automation Content Execution Environments list with network-ops-ee kebab open and Use in Controller selected.,link=self,window=blank]

* On **Create execution environment**, keep the pre-filled **Image** URL and enter `network-ops-ee` for the **Name**.
* Select  **Always pull container before running** for **Pull**.
* Set **Registry credential** to **`Private Automation Hub Registry`**.
* Click create / save.

=== Attach the EE to the Network job template

* Go to **Automation Execution → Templates**.
* Open **`Network/Onboard Network device`**.
* Edit the template.
* Set **Execution Environment** to **`network-ops-ee`**.
* Save.

== Learning outcomes

By completing this module, you should now understand:

* **Why purpose-built EEs matter** - Automation often needs a predictable runtime with the right collections and packages
* **How EE Builder works in the portal** - Guided selection of base image, collections, and packages publishes a definition to Git and starts a build
* **How Hub and Controller fit together** - Built images land in Private Automation Hub, then get attached to job templates in Controller before jobs can use them
* **How Catalog EE definitions work** - Shared EE metadata (`catalog-info.yaml`) can appear in the portal Catalog for discovery alongside templates and other assets

You discovered content in Module 4 and used it in Module 5 to close the loop from **discover → create → attach → sync → run** for execution environments in Automation Portal.
